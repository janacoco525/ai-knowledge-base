# AI知识库 — 概念串联与缺口提示契约

> **用途**：定义 `S2-01` 的最小输入输出结构，供后续 `/api/graph/chain`、前端提示面板与后续 GLM 施工共用
> **更新日期**：2026-05-07
> **状态**：active-owner

---

## 一、当前目标

这份契约先解决一件事：

- 当系统拿到一个概念时，后续应该如何返回“相关串联链”和“知识缺口提示”。

当前先定 **最小字段集 + 一份受控样例 payload**，不急着把完整智能串联链实现出来。

---

## 二、当前读法

- `S1-01 ~ S1-04` 已经把图谱链的基础结构、提取和只读展示收起来了。
- `S2-01` 的第一刀不是“马上做强智能”，而是先把返回格式定稳。
- 当前契约围绕 3 个核心字段：
  - `concept`
  - `related_chain`
  - `gap_hints`

---

## 三、最小请求结构

后续 `/api/graph/chain` 若落地，最小请求建议长这样：

```json
{
  "concept": "Attention",
  "domain": "ai_knowledge",
  "max_chain_steps": 4,
  "max_gap_hints": 3
}
```

### 字段说明

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `concept` | `string` | 是 | 当前要追踪的起点概念 |
| `domain` | `string` | 否 | 知识域，默认 `ai_knowledge` |
| `max_chain_steps` | `integer` | 否 | 最多返回几步串联链，建议 `2~6` |
| `max_gap_hints` | `integer` | 否 | 最多返回几个缺口提示，建议 `1~5` |

---

## 四、最小响应结构

最小响应统一长这样：

```json
{
  "version": "graph-chain.v1",
  "request": {
    "concept": "Attention",
    "domain": "ai_knowledge"
  },
  "related_chain": [],
  "gap_hints": [],
  "meta": {}
}
```

### 顶层字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `version` | `string` | 当前固定为 `graph-chain.v1` |
| `request` | `object` | 原始请求的最小回显 |
| `related_chain` | `array` | 当前概念出发的相关串联链 |
| `gap_hints` | `array` | 当前建议补足的概念缺口 |
| `meta` | `object` | 额外说明、告警、来源模式 |

---

## 五、`related_chain` 字段

`related_chain` 用于返回一条或多条“从当前概念出发的关联链”。

### 当前最小结构

```json
[
  {
    "chain_id": "attention-core-chain",
    "title": "Attention 到 Multi-Head Attention",
    "steps": [
      {
        "order": 1,
        "concept_id": "attention",
        "label": "Attention",
        "relation_from_prev": null,
        "source_file": "transformer-intro.md"
      }
    ],
    "summary": "从基础注意力到并行注意力头的核心演化链。"
  }
]
```

### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `chain_id` | `string` | 串联链唯一标识 |
| `title` | `string` | 这条链的短标题 |
| `steps` | `array` | 按顺序排列的概念节点 |
| `summary` | `string` | 这条链为什么成立的简短说明 |

### `steps` 子字段

| 字段 | 类型 | 说明 |
|------|------|------|
| `order` | `integer` | 第几步 |
| `concept_id` | `string` | 概念唯一标识 |
| `label` | `string` | 概念名 |
| `relation_from_prev` | `string/null` | 与前一步的关系，第一步允许为 `null` |
| `source_file` | `string` | 当前步主要来源文件 |

---

## 六、`gap_hints` 字段

`gap_hints` 用于提示“你已经走到了哪，但还缺哪块理解”。

### 当前最小结构

```json
[
  {
    "concept_id": "transformer",
    "label": "Transformer",
    "reason": "当前链已走到 Multi-Head Attention，但还未接到完整模块级理解。",
    "suggested_next_step": "补读 Transformer 总体结构与编码器-解码器关系。",
    "priority": "high"
  }
]
```

### 字段说明

| 字段 | 类型 | 说明 |
|------|------|------|
| `concept_id` | `string` | 缺口概念标识 |
| `label` | `string` | 缺口概念名 |
| `reason` | `string` | 为什么它是当前缺口 |
| `suggested_next_step` | `string` | 建议怎么补 |
| `priority` | `string` | 当前建议 `high / medium / low` |

---

## 七、当前最小样例

受控样例统一放这里：

- [graph-chain-sample.v1.json](output/graph/graph-chain-sample.v1.json)

当前样例只证明：

1. 可以从一个概念给出一条短链
2. 可以补出 1~2 个缺口提示
3. 后端、前端、后续模型可以围绕同一份格式继续做

---

## 八、当前不要做的事

1. 不要在这一步直接混入复杂 LLM 推理协议。
2. 不要先发明很多置信度、排序分数、图算法调参字段。
3. 不要把“缺口提示”写成泛泛而谈的学习建议，必须和当前链有关。
4. 不要让 `/api/graph/chain` 先落地再补契约，顺序反了会把后续执行带偏。

---

## 九、下一步

这份契约稳住后，下一刀才更适合是：

- `/api/graph/chain` 最小只读接口
- 或 React 图谱组件右侧面板消费 `related_chain / gap_hints`

但无论哪一刀，都先以这份契约为准，不要重新发明返回格式。
